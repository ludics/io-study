# 结论总结：网络 I/O 与磁盘 I/O，到底谁快谁慢

> 这是我们做了 8 个实现（epoll ×2 / io_uring ×3 / libaio / 同步 / libco）、
> 在两台 VM（内核 5.15 与 7.0）、扫过十几个维度之后得到的结论。
> 所有数字都是本项目实测，复现命令在各节末尾。
>
> 配套阅读：[04-epoll 编程](./04-epoll-编程指南.md)、
> [05-io_uring 编程](./05-io_uring-编程指南.md)、[06-libaio 编程](./06-libaio-编程指南.md)。

---

## 0. 先给结论

**「网络 I/O 和磁盘 I/O 哪个性能好」这个问法本身是不成立的** ——
它们是两套完全不同的物理约束，优化的杠杆也不一样：

| | 网络 I/O（回环） | 磁盘 I/O |
|---|---|---|
| 单次操作延迟 | **低**（回环 50-60µs 一个来回） | **高**（单次 128µs，四舍五入差 2 倍以上） |
| 吞吐的天花板由什么决定 | **CPU**（系统调用 / 唤醒 / 拷贝） | **设备队列深度**（盘能同时处理几个请求） |
| 唯一有效的扩展手段 | **加并发连接数 + 加核** | **加队列深度** |
| 同步方式的表现 | 单连接 ~1/RTT，加核几乎没用 | 在途数恒为 1，**完全吃不到深度红利** |
| epoll 能不能用 | ✅ 主战场 | ❌ **管不了普通文件**（文件永远"就绪"） |
| io_uring 能不能用 | ✅ | ✅ |

**如果非要比一个"谁快"**：单次操作的延迟，网络（回环）明显更低；
但两者的吞吐都**不是由介质决定的，而是由你在途请求数决定的** ——
这才是这次实验最重要的收获。

### 一句话版

- **网络**：赢在延迟和 CPU 效率。同一台机器上，现代 io_uring 单线程能到 **233k QPS**，
  是 epoll 单线程（112k）的 **2.08x**。
- **磁盘**：赢在"深度换吞吐"的空间大。同一份代码把深度从 1 拉到 32，
  IOPS 从 7.8k 涨到 **198.9k（25.5x）**；而同步方式**完全吃不到**这个红利。
- **同一个 API 在两边表现可能相反**：io_uring 在磁盘**读**上反超 libaio（235k vs 229k），
  在磁盘**写**上却明显吃亏（内核 5.15 上只有 libaio 的 **0.23x**，因为 `O_DIRECT` 写被
  punt 到 io-wq 工作线程池；内核 7.0 上这个差距基本消失，追到 **0.89x**）。

## 1. 网络 I/O 的结论

### 1.1 按实现排名（内核 7.0，16 线程 × 256B ping-pong，客户端绑核 0-3）

| 实现 | 核数 | QPS | 相对 epoll |
|---|---|---|---|
| epoll 单线程 | 1 | 112k | 1.00x |
| epoll 多 Reactor（4 worker + `SO_REUSEPORT`） | 4 | ≈4 worker × 单核，接近线性（实测 3.6x） | — |
| io_uring 基础版（每条消息提交一次） | 1 | 74.7k | **0.70x（更慢！）** |
| io_uring 全特性（开零拷贝） | 2 | 175 ~ 185k | 1.56 ~ 1.65x |
| **io_uring 全特性 + 关零拷贝** | 2 | **233k** | **2.08x** |
| libco（协程） | 1 | 数据不可信（见 §4.4） | — |

**四条结论**：

1. **epoll 单线程 ≈ 11 万 QPS 是"普通写法"的合理上限**。要更高必须多核，
   而多核的正确姿势是**每 worker 一个 listen fd + `SO_REUSEPORT`**（免锁免惊群），
   不是共享一个 epfd（那会惊群）。
2. **io_uring 不是"换了个 API 就快"**。基础版每条消息提交一次、立刻 `io_uring_enter` 一次
   （批量大小恒为 1），结果**比 epoll 还慢 30%**。
3. **io_uring 唯一能赢的路径是"把两条进内核的路都消掉"**：
   `SQPOLL`（提交不进内核）+ `CQ 忙轮询`（收割不进内核）。
   只开一个都会掉到 epoll 以下（只开 SQPOLL 63k；只开忙轮询 56.9k）。
4. **"少用系统调用"和"更快"是两件事**：
   把系统调用从 2.01 次/条降到 0.95 次/条，吞吐**几乎不动**；
   而从 1.02 次/条降到 **0** 才带来 3.2x。区别在于**省掉的是哪一次** ——
   省掉"等完成"才有用（进程不用睡下去再被唤醒），省掉"提交"没用。

### 1.2 延迟的真相

64 连接、256B 下：

| 实现 | QPS | p99 |
|---|---|---|
| epoll 单线程 | 11.3k | **20000µs（20ms）** |
| epoll 多 Reactor | 24.9k | 14105µs |
| io_uring 基础版 | 38.0k | 3708µs |
| io_uring 全特性 | 89.2k | 5451µs |

**epoll 的 p99 高不是因为 epoll 慢，而是因为排队**：它的吞吐只有 io_uring 的 1/8，
队列长 8 倍，尾延迟自然差一个量级。**读延迟数字前，先确认吞吐可比。**

### 1.3 网络侧的三个"反直觉"

1. **零拷贝发送（`SEND_ZC`）在小消息下是负收益**：同一个二进制只改这一个开关，
   **233k → 175k（-26%）**。因为每次发送多一个完成事件要处理，
   而 256B 消息省下的那次拷贝不值这个开销。
2. **「什么时候挂下一条 recv」差 1.55x**：收到完成就续挂（常驻可读）39k，
   改成"等回显发完再挂" **61.9k**。原因是回环下"发完再挂"时对端回复常已在
   socket 缓冲区里，recv 能在提交时**立即完成**；"常驻可读"则要走**异步轮询 + 唤醒**。
   perf 采样显示这类开销占了近 70% 的 CPU
   （`__wake_up_sync_key` 41.7% + `queued_spin_lock_slowpath` 27.4%）。
   ⚠️ 这是**回环环境放大**的效应，真实网络下常驻 recv 才是低延迟的正确姿势。
3. **SQPOLL 必须独占一个核**：同一个二进制，绑单核 15.4k，给两个核 63k。
   内核轮询线程和应用抢同一个核时，**比不开还慢**。

## 2. 磁盘 I/O 的结论

### 2.1 按实现排名（4KB / `O_DIRECT` / 深度 32，VM 本地盘 ext4）

> **测量介质**：测试文件在 **VM 本地盘**（`ext4` on `/dev/sda1`）上，**不是** sshfs。
> 这一点必须强调 —— 如果把测试文件放到 sshfs（网络文件系统）里，
> 「异步靠深度换吞吐」会**完全反过来**（实测 libaio 只有同步的 0.61x）。
> 详见 [测量环境与复现](../测量环境与复现.md)。

**内核 5.15.0-186**（每项 5 次取中位）：

| 实现 | 写 IOPS | 读 IOPS | 备注 |
|---|---|---|---|
| 同步（pread/pwrite） | 8,834 | 9,131 | **完全吃不到深度** |
| libaio | **220,388** | 234,941 | 需要 `O_DIRECT` |
| io_uring | 50,231（★ 只有 0.23x） | **240,829（反超）** | 写被 punt 到 io-wq（见 2.2） |

**内核 7.0.0-30**（同一台机器规格的另一个 VM，每项 5 次取中位）：

| 实现 | 写 IOPS | 读 IOPS | 备注 |
|---|---|---|---|
| 同步（pread/pwrite） | 8,531 | 8,794 | 同样吃不到深度 |
| libaio | 192,672 | 228,748 | — |
| io_uring | **171,035（0.89x）** | **234,557（反超）** | 写不再被 punt，差距基本消失 |

**同一个 API、同一组参数、同一块虚拟盘，只换内核版本，io_uring 的写从 0.23x 变成 0.89x。**
这是本项目里「结论依赖内核实现细节」最典型的一例。

### 2.2 三种实现的核心差别

1. **同步 I/O 的在途请求数恒为 1**，所以磁盘的并行能力完全用不上 ——
   加深度对同步没有任何意义（实测 7.8k 在深度 1→32 之间纹丝不动）。
2. **libaio / io_uring 的收益 100% 来自并发深度**：
   同一份代码，深度 1 → 32，写 IOPS 从 7,811 到 198,905（**25.5x**），
   读从 8,729 到 245,671（**28.1x**）。
3. **io_uring 写慢不是 API 的问题，是内核走了哪条路的问题 —— 而且这条路在变**：
   在 5.15 上跑写测试时，`ps -o comm= -L -p <PID>` 能看到 **15 个 `iou-wrk-*` 线程** ——
   `O_DIRECT` 写被内核甩给了异步工作线程池，每次 I/O 多一次跨线程交接；
   读不需要 punt，所以读不落后还反超。
   但在 **7.0 上同样的测试只剩 1 个 `iou-wrk-*` 线程**，写 IOPS 随之从 50k 涨到 171k。
   **异步 I/O 的瓶颈常常不在 API，而在内核走了哪条路 —— 并且那条路会随版本变。**
   所以看到「io_uring 写慢一半」这类结论时，第一件事是报上内核版本。

### 2.3 磁盘侧的两个"测了才知道"

1. **buffered I/O 的数字是假的**：同一块盘、同样的代码，加不加 `O_DIRECT`
   差 **10 倍**（1,984,205 vs 198,905 IOPS；7750 MB/s vs 777 MB/s）。
   buffered 测的是 page cache，不是磁盘。
2. **虚拟盘上的绝对值不可信**：本项目所有磁盘测试都跑在 QEMU 虚拟盘上，
   宿主机缓存会吸收写入。**只有相对关系可信**，要真正的绝对能力得用物理盘或直通盘。

## 3. 交叉对比：同一个 API 在两边的表现

| API | 网络 | 磁盘 |
|---|---|---|
| **同步 read/write** | 能用，但一个连接一个在途 = 1/RTT | 能用，但完全吃不到深度（7.8k） |
| **epoll** | **主战场**，单核 112k | **根本不适用**（文件永远"就绪"，`epoll_wait` 立刻返回后阻塞在 read 上） |
| **libaio** | **完全不支持 socket** | 写 220k / 读 235k |
| **io_uring** | 全特性 233k（2.08x epoll） | 读 241k（反超 libaio）；**写 50k~171k，随内核版本变化**（见 2.1） |

**这张表最值得记住的是三格**：

- epoll 那一格：**epoll 只能做网络**，这是它的能力边界，不是性能问题。
- io_uring 的磁盘写那一格：**同一个库在同一个介质上，不同操作方向差一倍** ——
  提醒你别把"某实现在某场景更快"当成普适结论。
- io_uring 网络那一格：**1.02 次系统调用/条 → 0 次，带来 3.2x**，
  这是整轮实验里唯一一次"量级"级别的提升。

## 4. 五条第一性原理（跨网络与磁盘都成立）

### 4.1 并发在途数决定吞吐，不是 API 决定吞吐

```
吞吐 ≈ 在途请求数 / 单次操作延迟      （Little's law）
```

- 网络：在途数 = **连接数**（每条连接保持 1 个在途请求）→ 所以要"加连接"。
- 磁盘：在途数 = **队列深度** → 所以要"加深度"。
- 同步 I/O 的在途数**恒为 1**，这是它永远打不出吞吐的根本原因。

**实测印证**：磁盘深度 1→32 → 25.5x；网络连接数 1→64 → 显著上升后趋于平台。

### 4.2 最贵的动作是"进内核去等"

```
把它当成成本排序：
  用户态共享内存读写（io_uring 的 SQ/CQ）      << 最便宜
  一次系统调用（提交）
  一次系统调用 + 睡下去 + 被唤醒（等待完成）    << 最贵
```

数据摆在这里：

| 配置 | 系统调用/条 | QPS |
|---|---|---|
| SQPOLL + 忙轮询 | **0.00** | **233k** |
| 只关忙轮询 | 0.14 | 56.9k |
| 两个都关 | 1.02 | 39.9k |
| adv 版（批量提交，但两者都没关） | 0.95 | 63.4k |

最后一行是关键：**系统调用降到 0.95 次/条，吞吐反而没涨**。
所以别数系统调用个数，要问「有没有省掉"等"」。

### 4.3 异步 ≠ 更快；异步 = 允许并发

磁盘那一格最直白：**同步和异步的单次延迟是同一个数量级**，
区别只在异步允许你在等待期间塞进去更多请求。
所以「异步」的价值随**并发需求**和**单次延迟**增长 ——
高延迟设备（磁盘）+ 高并发需求 = 收益最大；低延迟 + 低并发 = 白搭。

### 4.4 "看着高级"的特性经常不划算（必须用数据判断）

这次被实测否掉的"高级特性"：

| 特性 | 预期 | 实测 |
|---|---|---|
| 零拷贝发送 `SEND_ZC` | 省一次拷贝，更快 | **-26%**（小消息） |
| 固定文件表 / direct accept | 省 fget/fput，更快 | **打平**（7 轮 A/B 中位都是 222k） |
| 每个特性都打开 | 越多越好 | SQPOLL 单独打开**比不开还慢** |
| libco 协程 | 延迟更低 | 数据**不可复现**（见 §4.5） |

**方法上的教训**：任何优化都要留一个"只改这一个变量"的开关，并且交替多轮取中位，
否则很容易把噪声或环境效应当成收益。本项目所有实现都带环境变量开关，就是为这个。

### 4.5 测出来的数是"环境 + 用法"的函数

| 现象 | 真实原因 |
|---|---|
| libco 的 p99 比别人低一个量级 | **数据不自洽**：64 连接 / 350 QPS 反推平均延迟 183ms，却报 p50=116µs，差 1500 倍；重跑得到 31906 QPS，不可复现 |
| 三个服务端 QPS 挤在一起 | **压测端先饱和**（Python 多线程受 GIL 限制，单进程约 1 核到顶） |
| 磁盘 buffered 快 10 倍 | page cache 掩盖了真实磁盘行为 |
| 网络 io_uring 追平 epoll 却"没赢" | 用 Python 压测端测的，瓶颈在压测端 |
| aarch64 上 strace 抓不到 `epoll_wait` / `io_getevents` | 实际走 `epoll_pwait` / `io_pgetevents`（glibc 重定向） |

## 5. 选型指南

| 场景 | 推荐 | 理由 |
|---|---|---|
| 网络：连接多、每连接流量小（网关/代理/长连接） | **epoll**（多 Reactor + `SO_REUSEPORT`）或现代 io_uring | epoll 成熟稳定；追求极致吞吐上 io_uring（2.08x，但要给 SQPOLL 留核） |
| 网络：单连接高带宽（文件下载/转发） | 都行，重点用 `sendfile`/`splice` | 瓶颈在拷贝和带宽，不在就绪通知 |
| 网络：极低延迟（P99 敏感） | 先保吞吐，再看尾延迟 | 尾延迟主要由排队决定（实测 epoll 20ms vs io_uring 3.7ms 就是吞吐差 8 倍的后果） |
| 磁盘：高 IOPS（数据库/存储引擎） | **io_uring**（读）或 **libaio**（写，如果你在的内核上 io_uring 写被 punt） | 必须 `O_DIRECT` + 深度 |
| 磁盘：顺序大文件读写 | 同步 + `readahead` 就够 | 顺序访问本来就有预读，异步加成有限 |
| 内核 < 5.1 | libaio（磁盘）/ epoll（网络） | io_uring 不存在 |
| 容器环境 | 先测 `io_uring_setup` 是否被 seccomp 拦 | 默认策略常拦截，需要 `--security-opt seccomp=unconfined` |

## 6. ⚠️ 这些数字的适用范围（很重要）

诚实地说，本次实验有四个明显的局限，**结论的相对关系可信，绝对值需要你在自己的环境重测**：

0. **测量介质**：磁盘实验的测试文件在 **VM 本地盘**上（`ext4` on `/dev/sda1`），
   **不在 sshfs 上**；网络实验的数据面是 **VM 内回环**，与 sshfs 无关（实测二进制放 sshfs
   还是本地盘，网络 QPS 差别在噪声内）。这一点专门做了对照实验与全量审计，
   连同「为什么放 sshfs 会让异步结论反过来」都写在
   **[测量环境与复现](../测量环境与复现.md)** 里 —— 建议先读那份，再读本文的数字。

1. **网络全是回环（127.0.0.1）**，没有经过真实网卡。
   回环没有 DMA、软中断在发送方上下文里内联执行 —— 这放大了"唤醒"的开销
   （实测占近 70% CPU），真实网卡下比例完全不同。
   所以 **233k 这个数字不要当真**，要用 `bench_matrix.py` 在你的机器上重跑。
2. **磁盘全是 QEMU 虚拟盘**，宿主机缓存会吸收写入，绝对 IOPS 不可信。
   要真实数字得上物理盘 / 直通盘。
3. **压测端本身也是瓶颈之一**：Python 客户端受 GIL 限制（约 1 核到顶），
   所以本项目统一用 `bin/bench_client`（C++，无 GIL）。你在别的机器上复现时也要注意这点。

**相对关系（谁是 2x、谁是 0.7x、深度带来 25x、零拷贝 -26%）是可信的**，
因为它们来自同一台机器上的交替对照实验。
