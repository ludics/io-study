# 挂载方案对比：sshfs（multipass classic）vs virtiofs（native）

> 背景：本项目在两台 multipass 虚拟机里开发。宿主目录怎么进到 guest，直接决定了
> 「改代码 → 编译 → 跑测试」这个循环的体验。本文把两种方案的区别**实测**出来，
> 并给出实用的规避办法。
>
> 实测环境：宿主 macOS 14.6（Apple Silicon）/ multipass 1.16.3（QEMU 后端）；
> guest Ubuntu 26.04（内核 7.0）与 Ubuntu 22.04（内核 5.15）。

---

## 补充实测：sshfs 上「异步磁盘 I/O」的结论会反过来

这一条比性能差异更值得警惕 —— 它不改变速度，而是**改变结论**。

同一台 VM、同一份代码（`disk/io_libaio.c` 等）、同一组参数（4KB / `O_DIRECT` / 深度 32），
只改测试文件落在哪个文件系统：

| 测试文件位置 | 文件系统 | 同步写 IOPS | libaio 写 IOPS | **异步 ÷ 同步** |
| --- | --- | --- | --- | --- |
| VM 本地盘 | ext4 on `/dev/sda1` | 8,178 | **194,570** | **23.8x** ✅ |
| 工作区（本项目目录） | **fuse.sshfs** | 4,961 | 3,046 | **0.61x** ❌ |

**在 sshfs 上，异步 I/O 比同步还慢 39%。** 如果你的测试文件不小心落在项目目录里，
你会得出结论「异步 I/O 没有用」—— 而真正的磁盘完全不是这样。

### 更阴的地方：`O_DIRECT` 在 sshfs 上「打开成功但被忽略」

```
$ python3 -c "import os; os.open('/path/in/sshfs/x', os.O_RDWR|os.O_CREAT|os.O_DIRECT)"
O_DIRECT 打开: 成功        ← 没有报错
```

它不报错、程序照常跑、数字看着正常，但**完全没有绕过缓存**，测的也不是盘。
对比之下 tmpfs 至少会在内核 5.15 上明确返回 `EINVAL`。

### 另外：`/tmp` 不一定是磁盘

同一批实验在新 VM（Ubuntu 26.04 / 内核 7.0）上跑时，`/tmp` 是 **tmpfs（内存盘）**，
同步写测出 **1,634,328 IOPS**（比真实 NVMe 还快 4 倍）—— 那是内存的速度。

### 现在的护栏

`scripts/bench_matrix.py` 已经加了：

1. `--file` 默认值不再写死 `/tmp/...`，而是**自动挑一个落在真实块设备上的路径**；
2. 报告里显式标注 **★ 测量介质: ext4（挂载源 /dev/sda1）—— 本地块设备（可作基准）**；
3. 检测到 tmpfs / FUSE / NFS 一类介质时给出**带实测反例的强警告**；
4. 额外核对 `bin/.build-stamp`：多台机器共用一份挂载目录时，若产物不是本机编的就直接拒绝执行。

完整审计与对照实验见 **[测量环境与复现.md](./测量环境与复现.md)**。

## 1. 先澄清一个常见误解

**multipass 在 macOS 上的默认挂载就是 sshfs**，两台 VM 的参数**一模一样**：

```
sshfs -o slave -o transform_symlinks -o allow_other \
      -o Compression=no -o dir_cache=no \
      :/Users/ludi/workspace /home/ubuntu/workspace
```

```bash
$ multipass info exact-gerbil
Mounts:  /Users/ludi/workspace => /home/ubuntu/workspace
         UID map: 501:default
         GID map: 20:default
```

所谓 `--type classic`（默认）就是这套 sshfs；`--type native` 在 macOS 上是 virtiofs。
**两者不是"新旧 VM 的差别"，而是同一台 VM 可以选的两个挂载实现。**

## 2. 架构上的本质区别

### sshfs（classic）

```
  guest 里的文件操作
        │
     FUSE（用户态文件系统）
        │
   一个 sshfs 进程 ── SSH/SFTP 隧道 ──► 宿主上的 multipass 代理 ──► 真实文件
   （跑在 guest 里）
```

- 每一次文件操作都要**序列化成一个 SFTP 请求，穿过 SSH 隧道，再解析回来**；
- 所有操作**经过一个用户态进程**（FUSE + sshfs 双重上下文切换）；
- FUSE 强制 `-o allow_other`，且 `-o dir_cache=no` 关掉了目录缓存。

### virtiofs（native）

```
  guest 里的文件操作
        │
   virtio-fs 驱动（内核里）
        │
   virtio 队列（共享内存，不走网络协议栈）──► 宿主上的 virtiofsd ──► 真实文件
```

- 走的是**半虚拟化设备 + 共享内存队列**，不是网络协议；
- 有真正的内核客户端，支持 mmap/DAX、更完整的 POSIX 语义；
- **不需要 guest 里跑一个 FUSE 用户态进程**。

**一句话**：sshfs 是"用网络文件协议挂载一台远端机器"；virtiofs 是"把宿主目录变成一个虚拟块设备"。

## 3. 实测对比（sshfs vs VM 本地盘）

virtiofs 需要先关掉实例才能切换，所以下表是 **sshfs 与 VM 本地盘**的对比 ——
本地盘可以看作 virtiofs 性能的"上限参考"（virtiofs 通常能达到本地盘的 60~90%）。

| 操作 | sshfs 挂载 | VM 本地盘 | 差距 |
|---|---|---|---|
| 元数据 `stat`（冷，单次） | **420 µs** | 1 µs | **约 400x** |
| 元数据 `stat`（同一批再来一遍） | 1 µs（有属性缓存） | 1 µs | 打平 |
| 目录遍历（500 条目） | 273.7 ms | 3.6 ms | **76x** |
| 创建 1000 个小文件 | **2222 ms** | 13 ms | **171x** |
| 4KB 随机读（2000 次） | 848.6 ms / **424 µs/次** | 2.3 ms / 1.1 µs | **约 385x** |
| 8 线程并发写 64MB | 109 MB/s | 1691 MB/s | 15x |
| 顺序写 256MB | 164 MB/s | 1.6 GB/s | 10x |
| 顺序读 256MB | 165 MB/s | 5.7 GB/s | 35x |
| 编译（`make -B net`，8 次连续） | 全部成功 | 全部成功 | 稳定性一样 |

**读这张表的正确姿势**：

- **大块顺序读写差别只有 10~35 倍**（因为数据在批量传输，摊掉了每次往返开销）；
- **元数据和小文件操作差 170~400 倍**（每次都一个完整往返）——
  这正是"在挂载目录里跑 `git status`、`npm install`、编译几百个小文件会非常慢"的原因；
- **编译本身没有变得不可用**（8/8 成功），因为 gcc 读取的是内容而不是走大量元数据查询。

## 4. 功能上的边界（这些比性能更会让你踩坑）

| 能力 | sshfs | VM 本地盘 | 影响 |
|---|---|---|---|
| `mmap` 读写 | ✅ | ✅ | 没差别 |
| `O_DIRECT` | ✅（真的支持） | ✅ | 没差别 |
| 硬链接 / 符号链接 | ✅ 可创建 | ✅ | 但见下一行的坑 |
| **删除符号链接** | ❌ `rm: Value too large for defined data type`（EOVERFLOW） | ✅ | **sshfs 的实际 bug**，得从宿主侧删 |
| **`fallocate` 预分配** | ❌ 不支持 | ✅ | 数据库/存储引擎在这上面会退化 |
| **稀疏文件** | ❌ **不稀疏**：写 1 字节到 1GB 偏移会真的传 1GB | ✅ 实占 4KB | 会导致巨量无谓传输 |
| **`inotify` 能否感知宿主改动** | ❌ **不能**（guest 自己改能触发） | — | 文件监听类工具（webpack/vite/LSP 的 watch 模式）**在挂载目录上会失效** |
| 挂载目录里新建的文件 | 宿主侧新建后 guest **不是立刻**可见 | — | 见下一节 |

> 「guest 自己改能触发 inotify，宿主改不能」这一条实测确认：
> `inotifywait` 在 guest 里能收到 `MODIFY tick.txt`（guest 自己写的），
> 但宿主侧改动完全收不到事件。**这是 sshfs 的架构决定的** —— 它没有事件通道。

## 5. ⚠️ 最需要警惕的一条：属性缓存会让 `make` 判断失误

**实测数据**：宿主写完一个文件后，guest 侧 `stat` 到的 `size` 有 **7/10 次是旧值**，
要等 **437 ~ 984 ms**（约 1 秒）才能看到正确的值。

```bash
# 实测：宿主写入 50000 字节 → guest 立刻 stat
期望 50000 字节: 第 437 ms 后看到正确的 size
期望 100000 字节: 第 984 ms 后看到正确的 size
期望 200000 字节: 第 924 ms 后看到正确的 size
```

**但要分清两件事**（这点很关键，别过度恐慌）：

| 操作 | 会不会被"旧缓存"影响 |
|---|---|
| **读文件内容**（`cat`、`gcc` 读源码） | ❌ **不受影响**：实测宿主刚写完立刻 `cat`，5/5 次都拿到完整的新内容 |
| **看元数据**（`stat` 的 size/mtime） | ✅ **会受影响**：可能拿到最长约 1 秒前的旧值 |

**所以真正的坑只有一个**：`make` 靠 **mtime** 判断"要不要重编"。
宿主刚改完文件、你在 1 秒内跑 `make`，它可能认为目标是最新的而**跳过编译**。

规避办法（任选）：

```bash
# 1) 强制重编（本项目一直这么用，最省心）
make -B net

# 2) 或者保证编辑与构建之间隔 1 秒以上（人工操作其实天然满足）

# 3) 或者让 make 依赖挂载目录之外的标记文件（麻烦，不推荐）
```

## 6. 三种实用方案

### 方案 A：什么都不改，加一条纪律（零成本，推荐先试）

- 编译一律用 `make -B`（或确保编辑与编译间隔 > 1s）；
- 编译产物落到 VM 本地盘，绕开 sshfs 写大文件：

```bash
make net BINDIR=/home/ubuntu/iobin      # 产物不进挂载目录
```

- 不要把"需要文件监听的工具"（webpack watch、jest --watch、某些 LSP）指向挂载目录。

**实测结论**：本项目用这套纪律跑了整整两轮开发（两台 VM），
`make -B net` 连续 8 次全成功、大文件写 10 次全成功、500 个小文件创建 100% 成功。
**sshfs 是稳定的，只是慢。** 唯一遇到过一次 `ld: final link failed: Input/output error`，
重试即好（偶发）。

### 方案 B：只把"源代码"同步进 VM，在本地盘上编译（最稳，改动最小）

```bash
# 在 VM 里
rsync -a --delete /home/ubuntu/workspace/io-study/ /home/ubuntu/io-study-local/
cd /home/ubuntu/io-study-local && make -B all && bash scripts/bench_matrix.py net
```

好处：编译、测试、`git` 全在本地盘，完全摆脱 sshfs 的元数据开销和缓存问题。
代价：改完代码要记得同步一次（可以写成一个 `sync-and-build` 的小脚本）。

### 方案 C：换成 native（virtiofs）挂载 —— 需要重启 VM

```bash
multipass stop exact-gerbil
multipass unmount exact-gerbil:/home/ubuntu/workspace
multipass mount --type native /Users/ludi/workspace exact-gerbil:/home/ubuntu/workspace
multipass start exact-gerbil
```

**注意**：

- multipass 会明确要求先 stop（实测：`mount failed: Please stop the instance
  before attempting native mounts.`），所以这是**需要中断 VM 上正在跑的东西**的操作；
- 换完之后**建议用本文第 3 节的测试脚本重跑一遍**，确认元数据性能确实改善
  （预期能到本地盘的 60~90%，即元数据从 420µs 降到个位数 µs 量级）；
- `inotify` 在 virtiofs 上的行为需要**实测确认**（别假设它一定支持），
  换完之后用第 4 节的 `inotifywait` 方法测一下。

## 7. 一句话总结

| | sshfs（classic） | virtiofs（native） |
|---|---|---|
| 就地编译小项目 | 可用（大块 I/O 只慢 10~35 倍） | 明显更接近本地盘 |
| `git status` / 小文件密集操作 | **很慢**（元数据差 400 倍） | 好得多 |
| 稀疏文件 / `fallocate` | ❌ 不支持 | 支持 |
| `inotify` 监听宿主改动 | ❌ 不支持 | 需实测确认 |
| 属性缓存导致 `make` 误判 | 有（约 1 秒窗口） | 缓存更短/无 |
| 切换成本 | — | **需要重启 VM** |

**如果你只是"在挂载目录里编译一个项目"**：方案 A（`make -B` + `BINDIR` 指向本地盘）
就足够了，实测两轮开发零故障。

**如果你要在挂载目录里频繁跑 `git status`、大量小文件、或需要文件监听**
（前端项目、monorepo、数据库文件）：值得花一次重启换成 virtiofs。
