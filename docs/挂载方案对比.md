# 挂载方案对比：multipass native（9p）/ classic（sshfs）/ VM 本地盘

> 背景：本项目在两台 multipass 虚拟机里开发，宿主目录 `/Users/ludi/workspace` 挂进 guest。
> 挂载方式直接决定「改代码 → 编译 → 跑测试」这个循环的体验。
>
> 实测环境：宿主 macOS 14.6（Apple Silicon，12 核）/ multipass 1.16.3（QEMU 后端）；
> guest `exact-gerbil` = Ubuntu 26.04 / 内核 7.0.0-30（下称 **guest 7.0**），
> `secured-monitor` = Ubuntu 22.04 / 内核 5.15.0-191（下称 **guest 5.15**）。
>
> 结论摘要：**`--type native` 不是 virtiofs，而是 virtio-9p，且它比 sshfs 更慢**
> （除目录遍历外，几乎每一项都慢 1.2~4.2 倍）。它真正的优势不在速度，而在
> **元数据一致性**（没有属性缓存）和**POSIX 语义完整性**（稀疏文件/符号链接/`fallocate`），
> 代价是**完全不支持 `mmap`、也不支持 `inotify`**。

---

## 0. 先纠正一个我之前说错的事

我在前面几轮里写过「multipass 在 macOS 上 `--type native` 就是 virtiofs」——**这是错的**。
实测（换完之后 `findmnt`）：

```
$ findmnt -no TARGET,FSTYPE,OPTIONS /home/ubuntu/workspace
/home/ubuntu/workspace 9p rw,relatime,access=client,msize=512000,trans=virtio
```

是 **virtio-9p**（`trans=virtio`），不是 virtiofs。multipass 在 macOS + QEMU 后端上的
`native` 实现走的是 9p over virtio，`virtiofsd` 那一套并没有被用上。

连带的错误还有两条，一并纠正：

| 我之前写的 | 实测结果 |
| --- | --- |
| native 元数据会「从 420µs 降到个位数 µs」 | ❌ 实际是 **1.7 ms/次 stat**，比 sshfs 还慢 2.7 倍 |
| native「有真正的 mmap、支持 DAX」 | ❌ 9p 下 **`mmap` 直接失败**（`Invalid argument`） |

**教训**：`--type native` 这个名字暗示"用虚拟化原生能力、性能更好"，但在 macOS + QEMU 上
并不成立。**别按名字选挂载方式，要按实测选。**

## 1. 三方总览

| | **native（9p）** | **classic（sshfs）** | **VM 本地盘** |
| --- | --- | --- | --- |
| 传输路径 | virtio 队列 → QEMU 9p 服务 | FUSE 用户态进程 → SSH/SFTP 隧道 | 虚拟块设备（`/dev/sda1`, ext4） |
| guest 侧页缓存 | ❌ 无（`cache=none`） | ✅ 有（实测 125x 重复读收益） | ✅ 有 |
| 元数据一致性 | ✅ **无属性缓存，始终新鲜** | ⚠️ 约 1 秒属性缓存 | ✅ 新鲜 |
| `mmap` | ❌ 不支持 | ✅ 支持 | ✅ 支持 |
| `inotify` | ❌ **完全不工作**（连 guest 自己改都不触发） | ⚠️ guest 自己改能触发，宿主改不能 | ✅ 正常 |
| 稀疏文件 / `fallocate` / 符号链接 | ✅ 支持 | ❌ 不支持 | ✅ 支持 |
| 元数据性能 | 差（比 sshfs 再慢 2.7x） | 中 | 极快 |
| 目录遍历性能 | **好**（比 sshfs 快 17x） | 极差 | 极快 |
| 大块吞吐 | **26~27 MB/s** | 110~115 MB/s | 1.5 GB/s（页缓存） |
| 编译一个 9.5MB 的小项目 | 2.5 s | 2.5 s | 1.3 s |

**一句话**：**native（9p）在速度上没有优势，在语义和一致性上有真实优势，但缺了 `mmap` 和 `inotify`
这两块很难绕开的能力。**

## 2. 微基准实测

同一台 VM（guest 7.0）上**同时挂载两种介质**（另加 VM 本地盘做基准），
同一份代码、同一组参数，**两种顺序各跑一遍取中位**（`local→native→sshfs` 与反序），
两遍差异 <10%，下表取其中一遍：

| 指标（越小越好） | **VM 本地盘** | **native（9p）** | **sshfs** | 9p vs 本地 | sshfs vs 本地 | 9p vs sshfs |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 创建 2000 个 1KB 文件 | 24 ms | 6 962 ms | 5 246 ms | 290x | 219x | **9p 慢 1.3x** |
| `stat` 2000 次 | 2.2 ms | **3 264 ms** | 1 198 ms | 1 484x | 545x | **9p 慢 2.7x** |
| `listdir` ×200（目录 2000 项） | 75 ms | **1 299 ms** | **22 244 ms** | 17x | 297x | **9p 快 17x** |
| 读回 2000 个 1KB 文件 | 7.5 ms | 5 826 ms | 4 616 ms | 777x | 615x | 9p 慢 1.3x |
| 删除 2000 个文件 | 8.0 ms | 3 171 ms | 2 830 ms | 396x | 354x | 约持平 |
| `open`+`close` ×20000 | 16.9 ms | **39 468 ms** | 17 488 ms | 2 335x | 1 035x | **9p 慢 2.3x** |
| 顺序写 256MB | 1 484 MB/s | **26.8 MB/s** | **111 MB/s** | 55x | 13x | **9p 慢 4.2x** |
| 顺序读 256MB | 26.5 GB/s\* | **27.3 MB/s** | **110 MB/s** | — | — | **9p 慢 4.1x** |
| 4KB 随机读 | 0.8 µs | **316 µs** | 226 µs | 395x | 283x | **9p 慢 1.4x** |
| 遍历 3191 个文件的源码树 | 7.9 ms | **14 844 ms** | **3 813 ms** | 1 879x | 483x | **9p 慢 3.9x** |

\* 本地盘那两行大块数字是 **guest 的页缓存**（不是虚拟盘的真实能力），只作为"上限参考"。

**读这张表要注意三件事**：

1. **native 几乎全线落后**，唯一的例外是 `listdir`（目录项多时快 17 倍）——
   因为 sshfs 挂了 `-o dir_cache=no`，每次列目录都是一次完整往返。
2. **9p 的元数据延迟约 1.7 ms/次 `stat`、19.7 ms/次 `open+close`**，这个量级意味着
   在挂载目录里跑 `git status`、`npm install`、clangd 索引这类操作会非常难受。
3. **大块吞吐只有 26 MB/s**，比 sshfs 还慢 4 倍 —— 这与"native 应该更快"的直觉相反，
   原因见下一节。

## 3. 为什么 native 反而慢：它没有页缓存

`multipass mount --type native` 没有设置 9p 的 `cache=` 选项，于是 9p 以默认的
**`cache=none`** 运行 —— **每一次 `stat` / `open` / `read` / `write` 都是一次真实的协议往返**，
没有任何一层缓存挡在前面。

验证方法：反复读**同一个** 4KB 块，与读**不同的** 4KB 块对比。如果有页缓存，前者会快得多。

| 介质 | 读同一个块 | 读不同块 | 缓存收益 |
| --- | ---: | ---: | --- |
| VM 本地盘 | 0.4 µs | 0.4 µs | 两者都已缓存 |
| **native（9p）** | **316.6 µs** | **364.2 µs** | ❌ **几乎没有**（只有 1.15x） |
| **sshfs** | **0.4 µs** | **48.7 µs** | ✅ **有，125x** |

**这就是两者性能差异的根本原因**：sshfs 虽然协议更重，但它是 FUSE 文件系统，
**引入了 guest 页缓存**；9p 被配成 `cache=none`，**完全裸奔**。

再看"写吞吐 vs 单次块大小"，能看出两者都是**延迟受限**，但 9p 的每消息成本高得多：

| 单次写块大小 | native（9p） | sshfs | VM 本地盘 |
| ---: | ---: | ---: | ---: |
| 4 KB | 7.3 MB/s | 11.9 MB/s | 1 884 MB/s |
| 64 KB | 19.7 MB/s | 80.0 MB/s | 5 770 MB/s |
| 512 KB | 19.4 MB/s | 118.2 MB/s | 5 471 MB/s |
| 4 MB | 25.1 MB/s | 135.9 MB/s | 2 121 MB/s |

9p 无论给多大的块都上不去（7 → 25 MB/s），说明瓶颈是**协议往返本身**，
不是单次数据量；sshfs 则随块增大稳步提升（12 → 136 MB/s），符合"每次往返开销固定"的特征。

### 3.1 那给 9p 开缓存呢？—— 很快，但**不能用**

9p 支持 `cache=loose`。multipass 不暴露这个选项，而同一个 9p tag **不能被挂载两次**
（实测 `mount(2)` 也返回 `EBUSY`），所以只能卸掉再手工重挂。
我们**实测了一遍**（改完自动还原，原命令取自 guest 的 journal）：

| 指标 | `cache=none`（multipass 默认） | **`cache=loose`** | 提升 |
| --- | ---: | ---: | ---: |
| 顺序写 512KB 块 | 26.8 MB/s | **1 462 / 2 017 / 2 804 MB/s** | **55~100x** |
| 顺序读 | 27.3 MB/s | **11 184 / 12 081 / 11 904 MB/s** | ~430x |
| 读同一个 4KB 块 | 316 µs | **0.5 µs** | ~600x |
| `stat` ×500 | ~816 ms | **0.5 ms** | ~1 600x |

看起来非常美好，**但一致性直接崩了**。实测方法：guest 先读一次把缓存暖上，
然后**宿主把文件内容改掉**，guest 每 50ms 轮询一次，持续 18 秒：

```
  0.00s  size=  16  content=b'HOST-V1-ORIGINAL'
  （18 秒内再无任何变化）
  --- poller 结束后再强制读一次 ---
    HOST-V1-ORIGINAL        ← 宿主早已改成 HOST-V2，guest 完全看不到
```

**`cache=loose` 下宿主的改动对 guest 不可见**（9p over virtio 没有变更通知通道，
"loose" 的语义就是"信任服务端不会背着你改"）。
对你的工作流来说这是致命的：**在 Mac 上改完代码，VM 里编译的还是旧内容，而且没有任何报错。**

> 方向反过来倒没问题：guest 的写（含 `rm`）能到达宿主。
> 所以 `cache=loose` 适合"只读数据集"，**绝不适合共享的代码目录**。

**结论：不要用 `cache=loose`。** 想要快，正确做法是第 9 节 —— 把代码同步进 VM 本地盘再干活。

## 4. native 的真正优势：没有属性缓存，`make` 判断是对的

sshfs 最阴的坑是**约 1 秒的属性缓存**：宿主刚改完文件，guest `stat` 到的 `size`/`mtime`
有 7/10 次是旧值（实测 437~984 ms 后才更新），导致 `make` 可能认为目标是最新的而**跳过重编**。

**9p 上完全没有这个问题。** 实测方法（不依赖两端时钟）：

- 宿主以 **300 ms 间隔连续写 10 个版本**（`V00`~`V09`，每个版本长度不同）；
- guest 以 50 ms 间隔轮询，同时记录 **`stat().st_size`（走 getattr）** 和 **`read()` 的内容（走 open/read）**。

结果：

```
  0.00s  stat.size=   3  read.head=V00   一致
  5.52s  stat.size=  24  read.head=V01   一致
  5.83s  stat.size=  44  read.head=V02   一致
  ...
  8.08s  stat.size= 184  read.head=V09   一致

观测到 10 个不同的 (版本,大小) 组合（宿主写了 10 个：V00..V09）
```

**10 个版本全部看到、一个不漏，且 `stat` 报的大小与读到的内容始终一致。**
说明 9p 下每次 `getattr` 都真的问到了宿主 —— **`make` 不需要 `-B` 也能正确判断**。

> 这是**用速度换来的**：正因为没有缓存，它才总是新鲜的。见第 3 节末尾的取舍说明。

## 5. 功能边界（这些比性能更会让你踩坑）

| 能力 | **native（9p）** | **sshfs** | **VM 本地盘** |
| --- | --- | --- | --- |
| **`mmap` 读写** | ❌ **`Invalid argument`** | ✅ | ✅ |
| **`inotify`（guest 自己改）** | ❌ **收不到事件** | ✅ 能收到 | ✅ |
| **`inotify`（宿主改）** | ❌ 收不到 | ❌ 收不到 | — |
| `fallocate` 预分配 | ✅ 支持 | ❌ `Operation not supported` | ✅ |
| **稀疏文件** | ✅ 真稀疏（写 1 字节到 512MB 偏移，实占 0 MB） | ❌ **不稀疏**（真占 512 MB） | ✅ |
| 符号链接 创建/读取/删除 | ✅ 正常 | ❌ 创建时 `Permission denied` | ✅ |
| 硬链接 | ✅ `nlink=2` | ⚠️ `nlink` 不对 | ✅ |
| `rename` / `chmod` / `truncate` | ✅ | ✅ | ✅ |
| `O_DIRECT` 打开 | ✅（能否真正绕过缓存**未验证**） | ✅ **打开成功但被静默忽略** | ✅ |

两个最需要注意的：

- **`mmap` 不可用**。实测 `mmap()` 返回 `EINVAL`。这会打到一批常用工具：
  `git`（packfile 走 mmap，失败会退化到 `read`，变慢但能跑）、
  **clangd / LSP**（索引和源文件都走 mmap）、`ripgrep`（大文件）、部分编辑器和数据库。
  **如果你在 VM 里用 clangd，这一条足以让你放弃 9p 挂载。**
- **`inotify` 完全不工作**。实测连 **guest 自己创建/修改文件都没有事件**
  （sshfs 至少 guest 自己改是能触发的）。所以 watch 模式工具（vite/webpack/jest --watch、
  某些构建工具的增量监听）在 9p 挂载上会**静默失效**。

## 6. ⚠️ 两种挂载上都别跑磁盘 I/O 实验

这一条比性能差异更值得警惕 —— 它不改变速度，而是**改变结论**。
同一份代码、同一组参数（4KB / `O_DIRECT` / 深度 32），只改测试文件落在哪：

| 测试文件位置 | 同步写 IOPS | libaio 写 IOPS | io_uring 写 IOPS | **异步 ÷ 同步** |
| --- | ---: | ---: | ---: | ---: |
| **VM 本地盘**（ext4） | 7 565 | **98 195** | 55 951 | **13.0x / 7.4x** ✅ |
| **native（9p）** | 2 523 | 2 531 | 1 886 | **1.00x / 0.75x** ❌ |
| **sshfs** | 3 246 | 1 209 | 1 838 | **0.37x / 0.57x** ❌ |

读方向（本地盘 8 425 → libaio 122 640 → io_uring 221 235，即 14.6x / 26x）在两种挂载上
同样全部失效（9p 0.77x / 0.21x，sshfs 0.65x / 0.81x）。

**「异步靠并发深度换吞吐」这个结论，只有在真实块设备上才成立。**
在挂载目录里跑会得出完全相反的结论（"异步没用，甚至更慢"）。
原因和前面一样：**每次 I/O 都是一次协议往返，增大在飞请求数并不能减少往返次数**。

补充两个相关的坑：

- **`O_DIRECT` 在 sshfs 上是"打开成功但被静默忽略"** —— 不报错、程序照常跑、数字看着正常，
  但根本没绕过缓存。9p 上能否真正生效**我们没验证**，也应该当作"不可信"处理。
- **`/tmp` 不一定是磁盘**：guest 7.0 的 `/tmp` 是 **tmpfs（内存盘）**，同步写能测出
  **1 634 328 IOPS**（比真实 NVMe 还快 4 倍）。内核 5.15 的 tmpfs 会拒绝 `O_DIRECT`，
  而 7.0 的 tmpfs **静默接受**，后者更危险。

### 护栏（已进 `scripts/bench_matrix.py`）

1. `--file` 默认值不写死 `/tmp/...`，而是**自动挑一个落在真实块设备上的路径**；
2. 报告首屏显式标注 **★ 测量介质: ext4（挂载源 /dev/sda1）—— 本地块设备（可作基准）**；
3. 识别到 tmpfs / FUSE / **9p** 一类介质时给出**带实测反例的强警告**；
4. 核对 `bin/.build-stamp`：多台机器共用一份挂载目录时，若产物不是本机编的就**拒绝执行**。

完整审计见 **[测量环境与复现.md](./测量环境与复现.md)**。

## 7. 追查：`.2` 为什么多带 `sync,dirsync`，以及那 55 倍差异

### 7.1 `sync,dirsync` 是**内核加的**，不是 multipass 传的

两台是**同一条命令**挂的（用户确认），而且 guest 的 journal 里记着 multipass 真正执行的挂载命令 ——
**两台逐字相同、都没有传 `cache=`、也没有 `sync`/`dirsync`**：

```
$ sudo journalctl --no-pager | grep "mount -t 9p"
/usr/bin/mount -t 9p m40aa62ac5ede324399273d03bd6c52 /home/ubuntu/workspace \
    -o trans=virtio,version=9p2000.L,msize=536870912
```

答案在内核源码里。**5.15 的 `fs/9p/vfs_super.c` → `v9fs_fill_super()`**：

```c
sb->s_flags |= SB_ACTIVE | SB_DIRSYNC;        /* dirsync：无条件加 */
if (!v9ses->cache)                            /* cache=none 时： */
    sb->s_flags |= SB_SYNCHRONOUS;            /* sync */
```

multipass 没传 `cache=`，而 9p 的默认就是 `cache=none`，所以正好命中 ——
**`sync,dirsync` 是 9p 客户端在"无缓存模式"下自己设的 VFS 标志**，
`findmnt` 只是把它们显示出来了。

而**当前内核已经删掉了这两行**：

```c
sb->s_flags |= SB_ACTIVE;                     /* master：只剩这一个 */
```

→ 所以 `.2`（5.15）有、`.3`（7.0）没有。**这不是配置差异，是内核行为变化。**
（顺带：新内核还给 9p 客户端做了 netfs 改造 —— `v9fs_write_inode` 现在是
`netfs_unpin_writeback`，`drop_inode` 走 `inode_generic_drop`。这是个不小的重写。）

### 7.2 那 55 倍呢？现在有了新的证据

| guest | 内核 | 512KB 块顺序写（64MB×3） | 重复读同一块有无收益 |
| --- | --- | --- | --- |
| `exact-gerbil` | 7.0 | **25.5 / 27.6 / 25.1 MB/s** | 无（316µs ≈ 364µs） |
| `secured-monitor` | 5.15 | **1 390 / 1 454 / 1 670 MB/s** | 无（110µs ≈ 109µs） |

已排除：页缓存（两台都没有）、fsync 语义（加上不影响）、宿主路径差异（同一份目录）。
**注意上面第 3 节那个实验提供了关键对照：在 `.3` 上把同一个 9p 挂载改成 `cache=loose` 后，
写吞吐是 1 462 ~ 2 804 MB/s —— 和 `.2` 同一量级。** 这说明：

- **两台 guest 的 9p 传输能力没有本质差别**（`.3` 也能跑到 GB/s）；
- 差别在 **`cache=none` 时的写路径**上。

一个能同时解释所有观测的假设（**属推断，未最终证实**）：`.3` 在新内核 netfs 化的写路径下，
**大块写被拆成了接近页大小（4KB）的请求**，于是吞吐被"每请求固定开销"钉死。
验算一下：`.3` 实测 4KB 块 → 7.3 MB/s（≈156µs/次），512KB 块 → 19.4 MB/s
（≈27ms/次 ≈ 128 × 210µs）——**与"512KB 被拆成 128 个 4KB 请求"完全吻合**；
而 `.2` 的大块写没有这种拆分。

> **对使用者的意义**：如果你在意 bulk 吞吐且必须用 `cache=none`，两台的现状就是这样；
> 而正常做法不该是去调它，而是**别把大文件 I/O 放在共享目录里做**（见第 9 节）。

## 8. 实际编译耗时（决策真正该看的数字）

微基准差几百倍，但**实际编译一个小项目**差别很小：

```bash
make -B all examples        # 15 个目标，源码 9.5MB / 531 个文件，产物也落在同一介质
```

| 介质 | 第 1 轮 | 第 2 轮 |
| --- | ---: | ---: |
| VM 本地盘 | 1.36 s | 1.25 s |
| native（9p） | 2.58 s | 2.50 s |
| sshfs | 2.47 s | 2.62 s |

**两种挂载都是本地盘的约 2 倍，且彼此基本打平。**

为什么微基准差 300 倍、编译只差 2 倍？因为编译的**绝对耗时由 gcc 的 CPU 时间主导**，
读写量很小（9.5MB 源码、几百个小目标文件）。所以：

> **对"编译一下"这种工作流，挂载方式不是瓶颈；对"成千上万次元数据操作"
> （`git status`、`npm install`、LSP 索引、watch 模式）它才是。**

## 9. 推荐做法：把挂载降级成「编辑通道」，构建放在 VM 本地盘

### 9.1 一个关键的对照：传输本身走 SSH 比写挂载快 4 倍

如果挂载的定位是"同步代码和数据"，那它其实是个**传输通道** —— 而传输有更快的路：

| 方式 | 吞吐 | 落到哪里 |
| --- | ---: | --- |
| 写入 9p 挂载（native） | 22 ~ 27 MB/s | 挂载目录（9p → QEMU → 宿主） |
| 写入 sshfs 挂载（classic） | 110 ~ 115 MB/s | 挂载目录（FUSE → SSH → 宿主） |
| **`scp` / `rsync` → VM 本地盘** | **95 ~ 98 MB/s** | **VM 本地盘（ext4）** |

（256MB 单文件，各测 3 次；`scp` 那组是 95.0 / 98.5 / 94.7 MB/s。）

**关键不只是"快"**，而是**落点**：`scp` 的文件在 VM 的真实文件系统上，
编译、`git`、clangd、watch、`mmap`、稀疏文件、`inotify` **全部正常**；
而写在挂载目录里的文件，前面第 2~5 节那些坑一个都躲不掉。

### 9.2 所以推荐这个分工

```
   Mac（编辑 + 版本控制）                  VM（编译 + 跑测试）
   /Users/ludi/workspace/io-study   --rsync-->   /home/ubuntu/work/io-study
        ↑ 唯一真源                                    ↑ 构建镜像（可随时重来）
        └── 挂载目录只用于：浏览文件、偶尔直接改、看产物
```

- **代码**：`rsync` 到 VM 本地盘再构建；
- **数据**：大文件同样 `scp`/`rsync` 走 SSH，**不要**穿过挂载写；
- **挂载**：留着当"能看见 VM 文件"的便利通道即可，**别在里面构建、别指向 clangd**。

### 9.3 已经封装好：`scripts/vm-sync.sh`

```bash
bash scripts/vm-sync.sh          # 同步 + 冒烟构建（一条命令）
bash scripts/vm-sync.sh sync     # 只同步（rsync -az --delete，增量）
bash scripts/vm-sync.sh build    # 在 VM 本地盘上增量编译
bash scripts/vm-sync.sh test     # 在 VM 上跑矩阵压测
bash scripts/vm-sync.sh shell    # 进 VM 并 cd 到同步目录
```

默认同步到 `/home/ubuntu/work/io-study`（可用 `DST=` 覆盖，`VM=` 换目标机）。
它排除了 `bin/`、`results/`、`third_party/libco/build/`（**macOS 编的产物拿到 Linux 上会炸**）
等不该过去的目录。

**实测**：全量 78 个文件 / 1.0MB **1 秒内**完成，增量更快；VM 上 `make -B all examples`
15 个目标全部通过。

### 9.4 那挂载到底还用不用、选哪种

| 你的情况 | 建议 |
| --- | --- |
| **只要"同步代码/数据 + 在 VM 上编译测试"** | 挂载可有可无；用 `vm-sync.sh` 即可。**推荐直接这样** |
| 想在 Mac 上直接浏览/编辑 VM 里的文件 | 保留挂载，但**只当编辑通道**，构建仍走 `vm-sync.sh` |
| 上面这种情况下要 `mmap`（clangd / git 大仓库 / ripgrep） | **classic（sshfs）** |
| 上面这种情况下要 watch 模式（inotify） | **两者都不行**，必须走 `vm-sync.sh` |
| 要 `make` 判断准确、要稀疏文件/符号链接 | **native（9p）** |
| 目录项极多的目录遍历 | **native（9p）** |
| 要跑磁盘 I/O 性能实验 | **只能 VM 本地盘**，两种挂载都不行 |

**两条无论如何都建议保留的纪律**：

```bash
make -B net                         # 9p 下不必要，sshfs 下必要；留着无害
make net BINDIR=/home/ubuntu/iobin  # 万一必须在挂载目录里构建，至少让产物落本地盘
```

> **不要尝试用 `cache=loose` 换性能** —— 实测它会吞掉宿主的改动（第 3.1 节）。

## 10. 三种兜底方案

### 方案 A：接受现状 + 加纪律（零成本）

- 编译一律 `make -B`；产物落 VM 本地盘 `BINDIR=/home/ubuntu/iobin`；
- 不把 clangd 指向 9p 挂载目录；不把 watch 工具指向任何挂载目录。

**实测**：本项目用这套纪律跑了两轮开发（两台 VM），`make -B` 连续 8 次全成功、
大文件写 10 次全成功、500 个小文件创建 100% 成功。**两种挂载都是稳定的，只是慢。**
唯一遇到过一次 `ld: final link failed: Input/output error`，重试即好（偶发）。

### 方案 B：`vm-sync.sh` 同步到本地盘再构建（**推荐**）

见第 9 节。好处是编译/测试/`git`/clangd/watch 全部回到正常语义与全速，
代价只是"改完代码要同步一次"（一条命令）。

### 方案 C：在两种挂载之间切换 —— 需要重启 VM

```bash
multipass stop exact-gerbil
multipass umount exact-gerbil:/home/ubuntu/workspace      # 若已挂载
multipass mount --type classic /Users/ludi/workspace exact-gerbil:/home/ubuntu/workspace
multipass start exact-gerbil
```

- multipass 明确要求先 stop（实测：`mount failed: Please stop the instance before
  attempting native mounts.`），**会中断 VM 上正在跑的东西**；
- **换之前先想清楚要哪个**：要 `mmap`/`inotify` → classic（sshfs）；
  要元数据一致、稀疏文件、符号链接、目录遍历 → native（9p）；
- 换完**用本文第 2~5 节的方法重跑一遍**，别按名字假设性能。

## 11. 一句话总结

| | native（9p） | classic（sshfs） |
| --- | --- | --- |
| 速度 | 差（元数据比 sshfs 再慢 2.7x，大块吞吐只有它的 1/4） | 中 |
| 目录遍历 | **好（快 17x）** | 极差 |
| `make` 判断准确性 | **准（无属性缓存）** | ⚠️ 有 1 秒缓存窗口，需 `-B` |
| `mmap` | ❌ 不支持 | ✅ 支持 |
| `inotify` | ❌ 完全不工作 | ⚠️ 仅 guest 侧改动有效 |
| POSIX 语义（稀疏/符号链接/fallocate） | ✅ 完整 | ❌ 大量缺失 |
| 就地编译小项目 | 本地盘 2 倍 | 本地盘 2 倍 |
| 切换成本 | — | 需要重启 VM |

三句话：

1. **`--type native` 是个被名字误导的选项** —— 它不带来性能，带来的是语义正确性，
   代价是丢掉 `mmap` 和 `inotify`。
2. **换挂载解决不了根本问题**：两种挂载的元数据都比本地盘慢几百倍。
3. **正确的解法是把"同步"和"构建"分开**：`rsync`/`scp` 到 VM 本地盘（95~98 MB/s），
   在真实文件系统上编译测试 —— 这也是 `scripts/vm-sync.sh` 做的事。
