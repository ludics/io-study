# 测量环境与复现

> 这份文档回答两个问题：
> **① 之前所有的实验数字，到底是在什么介质上测出来的？**
> **② 我能在自己的机器（尤其是 macOS）上重跑吗？**
>
> 结论先说：**之前的实验都不是在 sshfs 上测的**，但**确实存在两类会让复现翻车的坑**，
> 而且其中一个（`.3` 的 `/tmp` 是内存盘）**差一点就污染了结论**。
> 下面把每个数字的来源、对照实验、以及新增的护栏都写清楚。

---

## 一、审计：每个数字测在哪

| 实验 | 数据面经过哪里 | 可执行文件在哪 | 测试文件在哪 | 可信度 |
| --- | --- | --- | --- | --- |
| 网络 echo（epoll / io_uring / adv / modern / libco） | **VM 内回环 `127.0.0.1`**，不经过 sshfs | `bin/`（sshfs） | 无 | ✅ 可信（见 §四实测：介质无影响） |
| 网络系统调用计数 / perf 采样 | 同上 | 同上 | 无 | ✅ 可信 |
| 磁盘三方对比（sync / libaio / io_uring） | VM 内 `/dev/sda1` | `bin/`（sshfs） | `.2`：`/tmp/iodemo_matrix`（ext4，本地盘） | ✅ 可信 |
| 磁盘多维矩阵（深度 / 块大小 / O_DIRECT） | 同上 | 同上 | 同上 | ✅ 可信 |
| libco 协程切换 / echo | VM 内 | `third_party/libco/build/`（sshfs） | 无 | ✅ 可信 |
| 挂载能力与性能对比 | — | — | 四个介质并列 | ✅ 可信 |

**为什么网络实验不受 sshfs 影响**：sshfs 只是「源码和可执行文件放在哪」。程序一旦被加载进内存，压测的数据面全程在 VM 内部的回环设备上，一个字节都不经过 sshfs。
（唯一可能的干扰是**动态库按需分页**，但那是启动时的一次性开销，稳态吞吐里已经不存在了 —— 见 §四的实测。）

**为什么磁盘实验必须看介质**：磁盘实验的测试**文件本身**放在哪，直接决定了「你测的是哪块设备」。放在 sshfs 上，测的就是「SFTP 协议栈 + 宿主机文件系统」，而不是盘。

## 二、设计给这个问题的对照实验

同一台 VM（Ubuntu 22.04 / 内核 5.15）、同一份代码、同一组参数（4KB / O_DIRECT / depth=32），只改测试文件所在的文件系统：

### 2.1 异步 I/O 能不能靠深度换吞吐

| 介质 | 文件系统 | 同步写 | libaio 写 | io_uring 写 | **异步 ÷ 同步** |
| --- | --- | --- | --- | --- | --- |
| VM 本地盘 | ext4 on `/dev/sda1` | 8,178 | **194,570** | 13,068 | **23.8x** ✅ |
| `/tmp`（同属根 fs） | ext4 on `/dev/sda1` | 8,160 | 164,769 | 15,074 | 20.2x ✅ |
| `/dev/shm` | tmpfs | — | — | — | O_DIRECT 被内核拒绝（`EINVAL`） |
| **工作区（sshfs）** | **fuse.sshfs** | 4,961 | 3,046 | 2,306 | **0.61x** ❌ |

**读法**：在 sshfs 上，**libaio 比同步还慢 39%**。如果当初把测试文件放进项目目录（也就是 sshfs 里），这篇项目文档的主结论会变成
> 「异步 I/O 没有用，甚至更慢」

—— 一个完全相反的结论，而且数字看起来毫无破绽。

### 2.2 顺序写带宽（dd 256MB + `conv=fsync`）

| 介质 | 带宽 | 相对 VM 本地盘 |
| --- | --- | --- |
| VM 本地盘（ext4） | 1.0 ~ 1.5 GB/s | 1x |
| `/dev/shm`（tmpfs） | 7.0 ~ 7.3 GB/s | ~5x |
| **sshfs** | **157 ~ 176 MB/s** | **~0.13x** |

### 2.3 内存盘有多危险

在新 VM（Ubuntu 26.04 / 内核 7.0）上，`/tmp` **是 tmpfs**。默认参数跑出来：

```
[A] 同步 (pread/pwrite)  block=4096  depth=32  direct=1 -> 写 1,634,328   读 2,609,657
```

**163 万 IOPS 的「同步写」** —— 这个数字如果被当成磁盘能力写进文档，会荒谬到什么程度：
它比真实 NVMe 的顺序写还快 4 倍，而且是「同步」方式测出来的。

同一台机器换到真实本地盘（`/var/tmp`）后：同步写 **8,105** —— **差了 200 倍**。

> 顺便一个内核行为差异：`O_DIRECT` 在 **5.15 的 tmpfs 上被拒绝**（打开返回 `EINVAL`），
> 在 **7.0 的 tmpfs 上被静默接受**（打开成功，但当然没有绕过任何缓存）。
> 后者更危险 —— 它不报错。

## 三、顺带挖出来的三个坑（都已在工具里加了护栏）

### 坑 1：两台 VM 共用一份 `bin/`，会互相覆盖

工作区通过 sshfs 挂载进两台 VM（22.04 与 26.04），`bin/` 是**同一份目录**。
各自 `make` 一次之后，**后编的那台会盖掉先编的那台**。现场症状：

```
./bin/io_libaio: error while loading shared libraries: libaio.so.1t64: cannot open shared object file
```

（`libaio.so.1t64` 是 Ubuntu 24.04+ 的库名，22.04 上没有。）

**护栏**：`make` 现在会在 `bin/.build-stamp` 写下 `主机名|内核|架构|时间`；
`scripts/bench_matrix.py` 开跑前核对，不匹配就**直接拒绝执行**（退出码 2）并告诉你怎么修，
而不是默默测出别台机器的产物。强行继续要显式加 `--ignore-bin-stamp`。

### 坑 2：默认测试文件落在 `/tmp`，而 `/tmp` 不一定是磁盘

**护栏**：`--file` 的默认值不再是写死的 `/tmp/iodemo_matrix`，而是**自动挑一个落在真实块设备上的路径**
（依次尝试 `/var/tmp` → `/tmp` → `$HOME` → 项目目录，跳过 tmpfs 与网络文件系统）。
报告里也新增了一行醒目的介质标注：

```
★ 测量介质: tmpfs（挂载源 tmpfs）—— 内存盘（数字无效！）
```

### 坑 3：`O_DIRECT` 在 sshfs 上「打开成功但被忽略」

这是最阴的一个：**没有报错**，程序照跑，数字看着正常，但完全没有绕过缓存，测的也不是盘。
（相比之下 tmpfs 至少会在 5.15 上明确报 `EINVAL`。）

**护栏**：检测到介质是 FUSE / NFS / CIFS / virtiofs 一类时，报告开头直接给出实测反例：

```
⚠️  介质是 fuse.sshfs（网络/远程文件系统）—— 异步 I/O 的结论在这里会失效！
     实测（同一台 VM、同一份代码、同一组参数）：
       VM 本地盘：同步 8.2k / libaio 195k  →  异步是同步的 23.8x
       sshfs    ：同步 5.0k / libaio 3.0k  →  异步只有同步的 0.61x
     更阴的是 O_DIRECT 在这里**打开成功但被忽略**，没有任何报错。
```

## 四、网络实验真的不受介质影响吗？—— 实测

上面说「不受影响」是推理，这里给数字。同一份源码编到两个位置，服务端分别从两处加载，
数据面都是 VM 内回环（内核 7.0，8 客户端线程，256B ping-pong）：

| 服务端二进制位置 | 第 1 次 | 第 2 次 |
| --- | --- | --- |
| `bin/`（sshfs 挂载） | 93,251 | 90,443 |
| `/home/ubuntu/iobin`（VM 本地盘） | 91,057 | 93,062 |

**差异在噪声范围内。** 结论：网络实验可以直接在 sshfs 工作区里跑，不必折腾。

但**如果你在意编译/启动速度**，把产物编到本地盘仍然有意义：

```bash
make net BINDIR=/home/ubuntu/iobin     # 源码仍在 sshfs，产物落本地盘
```

## 五、macOS 上能测什么、不能测什么

### 5.1 不能：Linux 专有实现

逐个尝试在 macOS（14.6 / Apple clang 16 / arm64）上编译的结果：

| 文件 | 结果 | 原因 |
| --- | --- | --- |
| `network/echo_epoll.c`、`echo_epoll_mt.c`、`reactor_server.c` | ❌ | `<sys/epoll.h>` 只有 Linux 有 |
| `network/echo_io_uring*.c`（3 个） | ❌ | `liburing.h` / io_uring 是 Linux 5.1+ 内核接口 |
| `disk/io_sync.c`、`io_libaio.c`、`io_uring_disk.c` | ❌ | `O_DIRECT` / `libaio.h` 均不存在 |
| `disk/epoll_nonblock_demo.c`、`epoll_starve_demo.c` | ❌ | 依赖 epoll |
| `examples/*.c`（3 个） | ❌ | 依赖 epoll / io_uring / libaio |
| **`network/bench.py`** | ✅ | 纯 Python，只用 socket |
| **`network/bench_client.cpp`** | ✅ | 只用 POSIX socket（`-std=c++17` 零警告） |

**这不是「代码写得不好」，而是接口不存在。** macOS 的对等物是：

| Linux | macOS 对等物 | 差异 |
| --- | --- | --- |
| `epoll` | **`kqueue`** | 编程模型相近（见下）；kqueue 用 `EV_CLEAR` 表示边缘触发 |
| `io_uring` | **无** | macOS 没有内核级异步 I/O 提交队列 |
| `libaio` | **无**（只有线程池实现的 POSIX AIO） | 是假异步 |
| `O_DIRECT` | `fcntl(fd, F_NOCACHE, 1)` | 只是「建议」，无对齐要求，不保证完全绕过缓存 |
| `taskset -c N` | 无 | macOS 没有 CPU 亲和性设置 |

### 5.2 能：已补上两个对等实现

| 文件 | 对应 Linux 的 | 说明 |
| --- | --- | --- |
| `network/echo_kqueue.c` | `echo_epoll.c` | kqueue 版单线程 Reactor，支持 `ECHO_NODELAY` / `ECHO_ET` |
| `disk/io_macos.c` | `io_sync.c` / `io_libaio.c` | `F_NOCACHE` + 多线程模拟并发深度 |

```bash
make macos
./bin/echo_kqueue 19000 &
./bin/bench_client 19000 8 256          # 或 python3 network/bench.py 19000 ...
./bin/io_macos /tmp/io_macos.dat 4096 8192 1 1 256
```

### 5.3 实测数字（宿主机真实硬件，非虚机）

**网络**（kqueue 单线程，回环）：

| 压测端 | 配置 | QPS |
| --- | --- | --- |
| C++（`bench_client`） | 8 线程 / 256B | **96,570** |
| C++（`bench_client`） | 16 线程 / 64B | **100,514** |
| Python（`bench.py`） | 8 线程 / 64 连接 / 256B | 58,250（GIL 上限） |

**磁盘**（APFS + `F_NOCACHE`，4KB，256MB 文件，各 3 次取中位）：

| 线程数（= 模拟的并发深度） | 写 IOPS | 读 IOPS |
| --- | --- | --- |
| 1（≈ `io_sync` 的深度 1） | **70,093 ~ 81,180** | 70,378 ~ 75,500 |
| 8 | 22,922 ~ 28,969 | 36,583 ~ 67,515 |
| 32 | 14,847 ~ 21,054 | 87,625 ~ 104,417 |

两个值得记住的点：

1. **多线程在 macOS 上并不能模拟出 libaio / io_uring 的效果 —— 写反而越并发越慢。**
   这正说明那两者存在的意义：把「并发深度」从线程里挪进内核。
2. **关掉 `F_NOCACHE` 后读变成 139 万 IOPS** —— page cache 把真实磁盘完全盖住了，
   和 Linux 上「buffered 虚高 100 倍」是同一个现象。

**与虚拟机对比**（同为 4KB O_DIRECT、同步方式、深度 1）：

| 环境 | 同步写 IOPS |
| --- | --- |
| 宿主机真实 NVMe（macOS，`F_NOCACHE`） | **70,093 ~ 81,180** |
| VM 虚拟盘（Ubuntu，ext4 on `/dev/sda1`） | **8,178 ~ 8,834** |

**约 9 倍差距**，这就是「虚拟磁盘」的代价。

## 六、一个重要的修正：io_uring 磁盘写的差距随内核版本变化

重测时发现，之前文档里写的「**io_uring 磁盘写只有 libaio 的一半**」在不同内核上差别很大：

| 内核 | io_uring 写 | libaio 写 | 比值 | 进程里的 `iou-wrk-*` 线程数 |
| --- | --- | --- | --- | --- |
| 5.15.0-186 | 50,231 | 220,388 | **0.23x** | **15 个** |
| 7.0.0-30 | 171,035 | 192,672 | **0.89x** | **1 个** |

（同一份代码、同一组参数、同一块虚拟盘，各 5 次取中位。线程数用 `ps -o comm= -L -p <pid>` 观察。）

**机制**：5.15 上内核会把 `O_DIRECT` 写**甩给 io-wq 异步工作线程池**处理（15 个 `iou-wrk-*` 线程），
每次 I/O 多一次跨线程交接；7.0 上基本不再 punt（只剩 1 个线程），所以差距基本消失。

**所以更准确的说法是**：
> io_uring 的磁盘**读**在所有内核上都持平或反超 libaio；
> 磁盘**写**在 5.15 上会明显吃亏（被 punt 到 io-wq），在 7.0 上已追到约 0.9x。

结论里那条「同一个 API 在两边表现可能相反」仍然成立，但要补一句：**这个「相反」本身也是内核版本相关的**。

## 七、复现命令

```bash
# ── 网络（Linux VM 或 macOS 都可）──────────────────────────────
make net                                   # Linux：编全部网络目标
make macos                                 # macOS：编 kqueue 版 + 压测客户端
./bin/echo_epoll 19000 &
python3 network/bench.py 19000 8 256 3 --conns 64      # Python 客户端
./bin/bench_client 19000 8 256                          # C++ 客户端（无 GIL）

# ── 磁盘（仅 Linux）────────────────────────────────────────────
make disk
python3 scripts/bench_matrix.py disk                    # 现在会自动挑真实本地盘
python3 scripts/bench_matrix.py disk --file /data/x     # 也可以显式指定

# ── 只想确认「你这个路径是什么介质」──────────────────────────
python3 - <<'EOF'
import importlib.util, sys
spec = importlib.util.spec_from_file_location("bm", "scripts/bench_matrix.py")
m = importlib.util.module_from_spec(spec); sys.modules["bm"] = m; spec.loader.exec_module(m)
for p in ["/var/tmp/x", "/tmp/x", "/dev/shm/x", "./x"]:
    med = m.probe_medium(p)
    print("%-22s %-12s %s" % (p, med["fstype"], m.MEDIUM_KIND_CN[med["kind"]]))
EOF
```

## 八、一句话总结

| 问题 | 答案 |
| --- | --- |
| 之前的实验是在 sshfs 上测的吗？ | **不是。** 网络数据面在 VM 回环；磁盘测试文件在 VM 本地盘（ext4 on `/dev/sda1`）。sshfs 只承载源码和可执行文件。 |
| sshfs 会影响结果吗？ | **网络：不影响**（实测 93k vs 91k，噪声内）。**磁盘：会彻底改变结论**（异步从 23.8x 变成 0.61x）。 |
| 之前的磁盘结论要改吗？ | **主体不用改**（本地盘重测复现了「深度换吞吐」26x 级的效果），但 **io_uring 写那一格要改**：它是分内核版本的（5.15 为 0.23x，7.0 为 0.89x）。 |
| 能在 macOS 上直接测吗？ | **这套 Linux 实现不能**（epoll / io_uring / libaio / O_DIRECT 都不存在）。已补 `echo_kqueue.c` 与 `io_macos.c`，压测客户端两边通用。 |
| 现在还会踩这些坑吗？ | 不会。构建戳校验 + 介质自动选择 + 介质强警告都已进工具。 |
