# 学习路径：从零到能自己判断 I/O 模型

这份文档写给「刚接触 Linux I/O，但想把原理搞扎实」的人。
原则只有一条：**每个概念都要有一个能跑出来、能看到数字的实验**，否则就是背结论。

---

## 一、先建立地图：三个概念轴

大部分「I/O 模型」的困惑，来自把不同轴上的概念混在一起谈。先把三根轴分开：

**轴 1：数据什么时候搬？（谁负责搬）**

| 模型 | 谁搬数据 | 代表 |
|------|---------|------|
| 阻塞式 | 调用线程自己搬，且搬运期间被挂住 | `read()` 默认行为 |
| Reactor（就绪通知） | 内核只告诉你「可以搬了」，**你自己搬** | `select` / `poll` / `epoll` |
| Proactor（完成通知） | **内核帮你搬好**，只告诉你「搬完了」 | `io_uring` / libaio / IOCP |

**轴 2：一次能等多少个 fd？**

`select`(1024 上限，O(n) 扫描) → `poll`(无上限，仍 O(n)) → `epoll`(内核维护红黑树+就绪链表，O(1))。

**轴 3：一次能让多少个 I/O 同时在飞？（并发深度）**

这是最容易被忽略、但对性能影响最大的一根轴。
同步 I/O 的并发深度恒等于 1；异步 I/O 的并发深度由你决定。
**磁盘上「异步比同步快 20 倍」这件事，本质是并发深度带来的，不是 API 带来的。**

> 记住这句话，它能解释本仓库里所有的性能数字：
> **QPS/IOPS ≈ 并发深度 ÷ 单次延迟**（Little's law）

## 二、需要的前置知识（不用精通，够用就行）

| 概念 | 需要知道到什么程度 | 在本仓库哪里能看到 |
|------|------------------|------------------|
| 文件描述符 fd | 「一切皆文件」，socket 和普通文件都是 fd | 所有代码 |
| 用户态 / 内核态 | 系统调用 = 主动陷入内核；这是 I/O 开销的主要来源 | `strace` 实验 |

| 上下文切换 | 线程切换 ~1µs，协程切换 ~10ns（用户态完成） | `libco/bench_swap.cpp` |

## 三、动手顺序（照着做，每步都要看到数字）

### 阶段 1：看懂「同步到底慢在哪」

```bash
bash scripts/check_env.sh          # 确认环境（io_uring 是否可用）
make disk && make bench            # 同步 vs libaio vs io_uring
```

要回答的问题：为什么 `DIRECT=1` 时异步能快 20~30 倍，而 `DIRECT=0` 时几乎没差别？

### 阶段 2：搞清 epoll 为什么必须配非阻塞

```bash
make bench_demo                    # 4 个对照实验，直接打印耗时
```

要回答的问题：为什么一个阻塞的 `read` 能拖死整个事件循环？（提示：事件循环是**单线程**的）

### 阶段 3：量化「并发深度」的收益

```bash
python3 scripts/bench_matrix.py disk      # 看维度 A：深度 1 → 32
```

要回答的问题：同步的 IOPS 为什么不随深度变化？libaio 为什么涨了 20 多倍？

### 阶段 4：理解 Reactor 与 Proactor 的差别

```bash
python3 scripts/bench_matrix.py net --mode full
strace -c -f ./bin/echo_epoll 19000 &      # 数系统调用（对比 io_uring）
```

要回答的问题：系统调用次数少，就一定更快吗？（提示：看压测端 CPU 占用那列）

### 阶段 5：协程为什么能「同步写法、异步性能」

```bash
make libco && ./bin/bench_swap
python3 scripts/bench_matrix.py net        # 对比 libco / epoll / io_uring 的 p99
```

要回答的问题：协程切换 10ns，那它的瓶颈在哪？为什么它的 p99 反而更低？

### 阶段 6（进阶）：自己改代码验证假设

这是真正开始「懂」的阶段。几个可以动手的改动：

1. 把 `echo_epoll.c` 的 ET 改成 LT（去掉 `EPOLLET`），性能/延迟有变化吗？
2. 给 `echo_io_uring.c` 加 `IORING_SETUP_SQPOLL`，系统调用数降到多少？
3. 把 `io_uring_disk.c` 的批大小从 depth 改成 depth×4，写 IOPS 会变好吗？
4. 给 `bench.py` 加上流水线（一条连接多个在途请求），吞吐还能涨吗？

## 四·五、怎么判断一次测量是否可信（这一步最容易被跳过）

拿到一组数字，先别急着下结论。按顺序问三个问题：

**1) 瓶颈在哪一边？**
被测对象（服务端）和测量工具（压测端）都会饱和。压测端先到顶时，
所有被测对象看起来"性能相当"，其实测的是压测端自己。
本项目里 Python 压测端受 GIL 限制，单进程约 1 核就到顶 —— 看它吃了几个核。

**2) 数据自洽吗？（Little's law 检验）**
每条连接保持 1 个在途请求时：`平均延迟 ≈ 连接数 / QPS`。
如果这个反推值比实测 p99 还大好几倍，说明**在途请求数根本没到连接数**，
那个"低延迟"是假的。

> 实例：我第一次测 libco 时看到 p99 只有 700~1100µs，而 epoll/io_uring 是 3000~4000µs，
> 差点得出"协程延迟更低"。一算：64 连接 / 350 QPS 反推平均延迟 ≈ **183 ms**，
> 和报出来的 p50=116µs 差了 1500 倍 —— 数据根本不成立。
> 后来重跑，同一个服务端跑出 31906 QPS，说明那次测量不可复现。
> `bench_matrix.py` 的「自动观察」现在会自动做这个检查。

**3) 结果可复现吗？**
同一个配置跑三遍，波动超过 20% 就先找原因（后台进程、CPU 频率、缓存状态），
别把噪声当成结论。本项目所有关键数字都至少跑过两遍。

## 四·六、同一个 API，换个用法能差 1.5~3 倍

学 I/O 最容易犯的错，是把「用了某个 API」当成结论。本项目里到处是反例：

| 看起来该赢的 | 实测 | 真正的原因 |
| --- | --- | --- |
| io_uring 比 epoll 新 | **0.70x**（更慢） | 基础版每条消息只提交 1 个 SQE，批量提交的收益是 0 |
| io_uring + SQPOLL | 0.85x（仍更慢） | SQ 内核线程吃掉一个核，而收割还要进内核 |
| io_uring + SQPOLL + CQ 忙轮询 | **1.77x** | 提交和收割**都不进内核**了，这才吃到红利 |
| 把 recv 挂得更早（常驻可读） | **0.63x** | 请求无法在提交时立即完成 → 走异步轮询 + 唤醒 |
| 异步 I/O（io_uring / libaio） | 同步的 27 倍 | 收益来自**并发深度**，不是 API 本身 |
| buffered 写比 O_DIRECT 快 100 倍 | 假象 | page cache 把真实磁盘行为整个盖住了 |
| 开零拷贝发送（SEND_ZC） | **0.75x**（更慢） | 每次发送多一个完成事件，小消息省下的拷贝不值 |
| 系统调用从 2.01 次/条降到 0.95 次/条 | 吞吐几乎不动 | 省掉的是"提交"，不是"等待/唤醒" |
| 系统调用从 1.02 次/条降到 0 次/条 | **3.2x**（72k→233k） | 省掉的是"等完成"，进程不再睡下去 |

所以看到「A 比 B 快」的结论，先问三个问题：

1. **A 和 B 的用法是对等的吗？** 本项目里 io_uring 的基础版和火力全开版是两个程序，
   结论完全相反 —— 拿基础版下结论会得到错误答案。
2. **瓶颈真的在被测对象上吗？** 系统调用次数、CPU、拷贝、唤醒，哪个是瓶颈？
   `perf stat` 数数、`perf record` 采样，比猜快得多。
3. **环境有没有放大/掩盖某个因素？** 本例中回环网络会把「异步轮询唤醒」的成本放大到
   70% CPU，这在真实网卡上完全不是这个比例。**测出来的是「环境」，不一定是「普遍规律」。**

一句话：**性能是「用法 + 环境」的函数，不是「API 名字」的函数。**

## 五、五个常见误区

1. **「异步一定更快」** —— 错。没有并发深度，异步只是更贵。buffered 模式下 libaio 常常比同步还慢。
2. **「epoll 比 select 快」** —— 只在**连接数很多**时成立。10 个连接时 `select` 可能更快（少一次内核注册）。
3. **「io_uring 是更快的 epoll」** —— 不是。它们是两种模型：epoll 通知就绪，io_uring 通知完成。
   io_uring 的收益来自**批量提交 + 少进内核**，用不好反而更慢（本仓库有实测）。
4. **「看 QPS 就够了」** —— 还要看 p99 和**瓶颈归属**。本仓库的矩阵工具会打印「压测端用了几个核」，
   就是为了防止把压测端的天花板当成被测对象的能力。
5. **「O_DIRECT 一定快」** —— O_DIRECT 是**绕过缓存**，不是加速。小 I/O 下它通常更慢，
   它的价值是（a）测真实磁盘能力（b）避免缓存污染。

## 六、怎么算「学明白了」

能不看资料回答下面这些，就说明真的懂了：

- 为什么 epoll 的 ET 模式必须配非阻塞？LT 模式配阻塞可以吗？为什么不行？
- 同步 I/O 的并发深度是多少？怎么提高它？
- libaio 为什么在 buffered 模式下会退化甚至报 EINVAL？
- io_uring 相对 epoll 省了哪些系统调用？在什么场景下这个节省才有意义？
- 为什么本仓库里 io_uring 的 O_DIRECT 写比 libaio 慢？怎么验证你的猜测？
- 单连接 QPS 上限由什么决定？64 连接时理论上限是多少？
